## 3. ความหน่วงของเครือข่าย ไทย → us-east-1

วัดด้วย `curl` ไปที่ `/health` (เส้นทางเต็ม: ALB → nginx → Internal ALB → Backend) 4 ครั้ง:

| ครั้ง | 1 | 2 | 3 | 4 | เฉลี่ย |
|---|---|---|---|---|---|
| เวลารวม (วินาที) | 0.636 | 0.538 | 0.512 | 0.533 | **0.555** |

`time_total` ของ curl รวมการเปิดการเชื่อมต่อ TCP (ไป-กลับ 1 รอบ) + ส่งคำขอและรับคำตอบ (อีก 1 รอบ) = ~2 รอบ → **เวลาไป-กลับ (RTT) ไทย ↔ Virginia ≈ 0.26 วินาที**

→ latency ของเกมผ่าน WebSocket (เชื่อมต่อค้างไว้แล้ว ใช้ 1 รอบต่อการกด) ที่วัดได้ ~300 ms (ข้อ 5) **ส่วนใหญ่ (~260 ms) คือระยะทาง** เวลาที่ระบบใช้จริงเหลือราว ~40 ms
→ ข้อเสนอ: ถ้าผู้ใช้หลักอยู่ไทย ควรใช้ region **ap-southeast-1 (สิงคโปร์)** — แต่ Learner Lab ใช้ได้เฉพาะ us-east-1 (ข้อจำกัดของการทดลอง)

## 4. ช่วงสร้างบัญชีบอท 150 บัญชี

- บอทเว้นจังหวะ ~6.5 วินาที/บัญชี เพื่อไม่ให้เกินลิมิต 10 ครั้ง/นาที → 150 บัญชีใช้ ~16 นาที
- **ขนาดข้อมูลต่อการสมัคร 1 คน** (วัดด้วย `information_schema` หลัง `ANALYZE TABLE`):

| ตาราง | avg_row_length | index ต่อแถว | แถวต่อคน |
|---|---|---|---|
| users | 323 B | 32768 ÷ 152 ≈ 216 B | 1 |
| wallets | 107 B | 0 | 1 |
| transactions (โบนัสต้อนรับ) | 186 B | 65536 ÷ 527 ≈ 124 B | 1 |
| **รวม** | | | **≈ 0.96 KB / คน** |

→ ข้อสมมติในรายงาน "1 user ≈ 1 KB" **ถูกต้องสำหรับข้อมูลตอนสมัคร**

- ระหว่างรันรอบที่ 2 พบว่าการเช็คบัญชี 150 ครั้งติดต่อกันจาก IP เดียวโดนจำกัด (HTTP 429) — **ยืนยันว่าระบบจำกัดอัตราคำขอทำงานจริง** (ผู้เล่นจริงแต่ละคนมี IP ของตัวเอง จึงไม่โดน) • ปรับสคริปต์บอทให้เว้นจังหวะแล้ว

## 7. ข้อจำกัดของการทดสอบ (ควรเขียนในรายงาน)

1. บอทยิงจากคอมเครื่องเดียว/IP เดียว — เกิน ~150–200 บอท เครื่องหรือเน็ตผู้ทดสอบอาจเป็นคอขวดเอง และโดนลิมิตต่อ IP
2. latency ฝั่งบอทรวมระยะทางไทย ↔ us-east-1 (~260 ms) — ใช้ ALB TargetResponseTime แทนเวลาฝั่งเซิร์ฟเวอร์
3. บอทเล่นเร็วกว่าคนจริงมาก → โหลดสูงกว่าใช้งานจริง (ตัวเลขที่ได้จึงเป็นค่าที่ปลอดภัยไว้ก่อน)
4. บอทไม่ได้เปิดหน้ารายชื่อห้อง/ประวัติ (ส่วนที่อ่านจาก read replica) — replica จึงมีโหลดน้อยในการทดสอบนี้
5. Test1–2 ทดสอบที่ Backend 1 เครื่อง • Test3 มี 2 เครื่อง + กฎ scale ตาม CPU 30 % แต่โหลดไม่ถึงจุด scale → ยังไม่ได้เห็น scale-out จริง (จุด scale เป็นการประมาณ)
6. EC2 t3 / RDS t4g เป็นแบบ burstable (โหมด Unlimited) — ใช้ CPU เกินระดับพื้นฐานนานๆ มีค่าใช้จ่ายเพิ่ม
