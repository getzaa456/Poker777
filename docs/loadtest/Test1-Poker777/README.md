## อ่านผลทีละส่วน

### 1. ความสามารถรองรับผู้เล่น (Backend)
- CPU เฉลี่ยช่วงเล่น: ว่าง 1.1 % → 50 คน 3.0 % → 100 คน 5.7 % → 150 คน 7.6 % = **เส้นตรง ≈ +0.046 % ต่อผู้เล่น**
- **t3.micro มี 2 vCPU** แต่ Node.js ทำงานบน **1 core** → CloudWatch **~50 % = core นั้นเต็มแล้ว**
- ประมาณการ: core เต็ม (50 %) ≈ (50 − 0.7) ÷ 0.046 ≈ **1,000 คน/เครื่อง** • ใช้แค่ 70 % ของ core (35 %) ≈ **700 คน/เครื่อง**
- บอทกดเร็วกว่าคน (ทุก 1–2 วินาที) → ตัวเลขนี้ **ปลอดภัยไว้ก่อน**
- ทั้งระบบ: ASG สูงสุด 2 เครื่องตามที่ตั้ง ≈ 1,400 คนพร้อมกัน • ผู้ใช้ต่อวัน (เล่นวันละ 3 ชม. = 12.5 %, พีค ~2.5 เท่าของเฉลี่ย): 700 ÷ 0.125 ÷ 2.5 ≈ **2,200 ผู้ใช้/วัน/Backend 1 เครื่อง**
- Frontend (nginx) CPU ≤ 1 % — ไม่ใช่คอขวด

### 2. Load Balancer (ALB)
- เวลาตอบใน AWS p95 16–42 ms ทุกขั้น ไม่โตตามผู้เล่น
- **ข้อจำกัด:** `TargetResponseTime` นับเฉพาะคำขอ REST — ข้อความ WebSocket ระหว่างเล่นเกม ALB ไม่จับเวลา จึงใช้ latency ฝั่งบอทประกอบ
- เชื่อมต่อค้าง 33 → 60 → 163 → 249 → **344** (~2.3 ต่อผู้เล่น) • Public / Internal ALB กราฟใกล้กัน → nginx ส่งต่อไม่เป็นคอขวด
- LCU (หน่วยคิดเงินของ ALB) 0.017 ใน 5 นาทีที่ 150 คน — เล็กมาก
- 5xx = 0 ทุกขั้น

### 3. RDS MySQL

CPU ทุกเครื่องช่วงเล่น (เฉลี่ย / สูงสุดรายนาที, %) — เทียบกับ baseline ที่ไม่มีผู้เล่น:

| ช่วง | writer | read-1 | read-2 | read-3 |
|---|---|---|---|---|
| **ไม่มีผู้เล่น** (17:02–17:07) | 4.8 / 5.1 | 4.6 / 5.0 | 5.0 / 5.8 | 4.7 / 5.3 |
| 10 คน | 5.1 / 6.4 | 4.3 / 4.9 | 4.2 / 4.5 | 4.5 / 5.2 |
| 25 คน | 4.7 / 5.7 | 4.5 / 5.9 | 4.6 / 6.2 | 4.8 / 7.5 |
| 50 คน | 4.7 / 5.1 | 4.5 / 5.0 | 4.5 / 4.7 | 4.6 / 5.6 |
| 100 คน | 4.9 / 5.4 | 4.8 / 5.4 | 4.8 / 5.2 | 4.9 / 5.9 |
| 150 คน | 5.4 / 5.8 | 5.2 / 5.7 | 5.0 / 5.5 | 5.1 / 5.8 |

- **CPU แทบไม่เปลี่ยนจากตอนไม่มีผู้เล่น** — จุดแหลมในกราฟ (ถึง ~8 %) เกิดแม้ไม่มีคน = งานเบื้องหลังของ MySQL/AWS ไม่ใช่จากเกม
- งานที่เพิ่มจริงคือ **write IOPS ของ writer: 0.7 → 8.6 → 26.7 → 53.9 → 76.5** (≈ 0.5 IOPS ต่อผู้เล่น) — gp3 ให้ 3,000 IOPS → ยังห่างมาก
- Write latency คงที่ 0.7–0.8 ms
- Connections: writer 15 (pool ของ Backend) • replica 1 ตัวละ (Test1 บอทไม่ได้เปิดหน้าที่อ่านจาก replica — read IOPS ของ replica < 1 ตลอด)
- Free memory ทุกเครื่อง ~95–117 MB คงที่ (db.t4g.micro RAM น้อย แต่ไม่ลดลง)
- Replica lag 0 s — แตะ 1 s ครั้งเดียวที่ 150 คน

### 4. Redis (ElastiCache)
- CPU primary: 0.3 % (ว่าง) → 0.8 → 1.0 → 1.9 → 3.4 → **4.4 %** (≈ +0.027 % ต่อผู้เล่น → หลายพันคนก่อนเป็นปัญหา) • replica node ~ครึ่งหนึ่ง
- Network out ของ primary 8.5 → 78.7 MB ต่อขั้น (pub/sub กระจายสถานะโต๊ะ + replication)
- Memory ~7 MB คงที่ (เก็บเฉพาะโต๊ะที่กำลังเล่น)

### 5. ขนาดข้อมูล (สำหรับประมาณการ storage)
วัด `information_schema` ก่อนขั้น 1 และหลังขั้น 5 (ผ่าน SSM บนเครื่อง Backend):

| | ก่อน | หลัง | เพิ่ม |
|---|---|---|---|
| hand_results (แถว / data+index) | 1,561 / 442,368 B | 4,505 / 2,162,688 B | +2,944 แถว / +1,720,320 B |
| transactions (แถว / data+index) | 1,692 / 507,904 B | 4,542 / 2,129,920 B | +2,850 แถว / +1,622,016 B |

- 1 แถว `hand_results` = ผู้เล่น 1 คนใน 1 มือ • ธุรกรรม ~0.97 แถวต่อผู้เล่นต่อมือ
- **ผู้เล่น 1 คน 1 มือ ≈ 3,342,336 B ÷ 2,944 ≈ 1.14 KB บนดิสก์จริง** (รวมพื้นที่ว่างในหน้า 16 KB ของ InnoDB)
- ⚠️ **Test2 วัดซ้ำด้วยข้อมูลมากกว่า 8 เท่าได้ ~0.61–0.65 KB** — ค่า 1.14 KB นี้สูงเพราะตารางยังเล็ก (MySQL จองพื้นที่เป็นก้อน) → **ใช้ตัวเลขของ Test2 ในรายงาน** (117 KB/คน/วัน, 20 GB เต็มใน ~170 วันที่ 1,000 ผู้เล่น/วัน)

### 6. Network
- Backend ส่งออก 58.7 MB ใน 5.1 นาทีที่ 150 คน ≈ **77 KB ต่อผู้เล่นต่อนาที** (ประมาณค่า data transfer)

## ข้อจำกัดของการทดสอบ
1. บอททั้งหมดยิงจากคอมเครื่องเดียว IP เดียวในไทย — latency รวมระยะทาง ~260 ms และโดนลิมิต 100 คำขอ/นาที/IP ช่วงเริ่ม
2. บอทเล่นเร็วกว่าคน → โหลดสูงกว่าจริง
3. ยังไม่ถึงจุดที่ระบบตัน — ความจุสูงสุดเป็นการประมาณจากเส้นตรง (Test2 ทดสอบ 300 / 700 / 1,000 คน)
4. ไม่มีการเปิดหน้าที่อ่านจาก read replica และไม่ได้วัด RAM ของ Backend (มีใน Test2)
5. Backend 1 เครื่องตลอด — ASG ยังไม่มีกฎขยายเครื่องอัตโนมัติ
