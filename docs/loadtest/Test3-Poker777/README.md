### 2. ประสบการณ์ผู้เล่น (Latency)
- p50 288 / 294 / 297 ms (Test2: 307–308) — ~260 ms เป็นระยะทางไทย ↔ Virginia → เวลาในระบบ ~30–40 ms
- **p95 ขั้น 700: 396 ms (Test2: 627 ms)** — ใน Test2 ช่วงจัดโต๊ะ (บอทเข้าห้องจำนวนมากพร้อมกับที่บอทอื่นกำลังเล่น) ทำให้ช้า • Test3 บรรทัดแรกหลังนั่งครบ (`step2-700bots/bots-timeline.csv`) p95 = 396 ms ตั้งแต่ต้น → **2 เครื่องช่วยรับช่วง join storm ได้**
- p95 ทั้ง 3 ขั้นอยู่ในช่วงแคบ 386–401 ms = เพิ่มผู้เล่นแล้วไม่ช้าลง

### 3. Auto Scaling — ทำไมไม่ scale และจะ scale เมื่อไร
- กฎ: รักษา **CPU เฉลี่ยของกลุ่ม** ไว้ที่ 30 % — AWS สร้าง alarm `AlarmHigh` (เกิน 30 % ติดกัน 3 นาที → เพิ่มเครื่อง) และ `AlarmLow` (ต่ำนาน → ลดเครื่อง แต่ไม่ต่ำกว่า min 2)
- ค่าเฉลี่ยสูงสุดที่วัดได้ 17.0 % (สูงสุดรายนาที 20.3 %) → **AlarmHigh ไม่ติด จึงไม่มี scale-out** — `14-asg-instances.png` เส้นตรงที่ 2 และ `asg-timeline.csv` เป็น 2/2 ตลอด 70 นาที = **ระบบไม่เพิ่มเครื่องโดยไม่จำเป็น (ไม่เปลืองเงิน)**
- ประมาณจุดที่จะ scale (CPU เฉลี่ยถึง 30 %):
  - ตามความชันช่วงท้าย (700 → 1,000: +0.009 %/คน) → **~2,400 คน**
  - แบบปลอดภัย (ความชันช่วงแรก 0 → 300: +0.014 %/คน) → **~1,900 คน**
  - เขียนในรายงาน: **"Auto Scaling จะเริ่มเพิ่มเครื่องราว 1,800–2,400 ผู้เล่น"** — สูงสุด 4 เครื่องรองรับได้ราว **~4,000 คน** (ก่อนถึงจุดนั้น Redis อาจกลายเป็นคอขวดก่อน — ข้อ 5)
- ถ้าอยากเห็น scale-out จริงในกราฟ: รันซ้ำด้วยเป้าต่ำลง `terraform apply -var backend_cpu_target=15` (เฉพาะการทดสอบ — ใช้จริงควรกลับเป็น 30)

### 4. Load Balancer
- REST ใน AWS p95 16.7 / 18.3 / **39.1 ms** — ขั้น 1,000 สูงกว่า Test2 (22 ms) แต่ p50 ยัง 9.7 ms และ internal ALB p95 22 ms → ส่วนหาง (p95/p99) ของคำขอไม่กี่ร้อยครั้ง/5 นาที ยังต่ำกว่า 50 ms
- เชื่อมต่อค้างสูงสุด 810 / 1,874 / 2,003 • 5xx = 0 ทุกขั้น (Test2 มี 1 ครั้ง)
- Frontend (nginx 2 เครื่อง) CPU 1.1 → 2.3 %

### 5. Redis — ส่วนที่ "แพงขึ้น" เมื่อมีหลายเครื่อง
| 1,000 คน | Test2 (1 Backend) | Test3 (2 Backend) |
|---|---|---|
| Redis primary CPU สูงสุด | 12.5 % | **17.4 %** |
| Network out (5 นาที) | 363 MB | **478 MB** |
| Connections | 8 | 11 |

- เหตุผล: **ทุก Backend subscribe pub/sub** → สถานะโต๊ะ 1 ข้อความถูกส่งให้ 2 เครื่อง และ **ทุก Backend poll ตัวจับเวลาใน Redis ทุก 0.5 วิ** → งานพื้นฐานเพิ่มตามจำนวนเครื่อง
- ข้อสังเกตสำหรับรายงาน: **เพิ่ม Backend = Backend เบาลง แต่ Redis หนักขึ้น** — Redis (cache.t3.micro, thread เดียว) จะเป็นตัวถัดไปที่ต้องขยาย (เครื่องใหญ่ขึ้น หรือแยก pub/sub) ถ้าจะไปหลายพันคน
- memory ~7.7 MB เท่าเดิม

### 6. RDS
- Writer CPU 5.8 → 7.0 → 8.0 % (Test2: 5.6 → 7.2 → 8.0) — **เท่ากับ Test2** เพราะงานเขียนขึ้นกับจำนวนมือ ไม่ใช่จำนวน Backend
- Write IOPS 104 → 120 → 145 • write latency 0.82 → 0.70 → 0.68 ms • replica lag ≤ 1 s
- Writer connections 21–24 (Test2: 15) = pool ของ 2 Backend • replica CPU ≤ 7.2 %

## ข้อจำกัด
1. บอทยิงจากคอมเครื่องเดียว IP เดียวในไทย (ลิมิต 100 คำขอ/นาที/IP → จัดโต๊ะ 6–19 นาที, เน็ตบ้านตัดทำให้ขั้น 3 ต้องรันซ้ำ)
2. บอทเล่นเร็วกว่าคนจริง → โหลดต่อคนสูงกว่าจริง
3. ไม่ได้ทดสอบจนเกิด scale-out จริง (CPU ไม่ถึง 30 %) — จุด scale เป็นการประมาณ
4. เครื่อง Backend เก่ายังมีบัคตัวจับเวลาค้าง (แก้ในโค้ดแล้ว ยังไม่ deploy) → CPU สองเครื่องไม่เท่ากันพอดี
5. Latency ของบอทเป็นค่าสะสมตั้งแต่มือแรก (รวมช่วงจัดโต๊ะ)
