## อ่านผลทีละส่วน

### 1. ความสามารถรองรับผู้เล่น (Backend)

**1.1 CPU** — รวม Test1 + Test2 (CPU เฉลี่ยช่วงเล่น):

| ผู้เล่น | 50 | 100 | 150 | 300 | 700 | 1,000 |
|---|---|---|---|---|---|---|
| Backend CPU | 3.0 % | 5.7 % | 7.6 % | 12.2 % | 20.6 % | 24.6 % |
| เพิ่มต่อผู้เล่น (จากขั้นก่อน) | — | 0.054 % | 0.038 % | 0.031 % | 0.021 % | 0.013 % |

- **CPU โตช้าลงเรื่อยๆ (ไม่ใช่เส้นตรง)** — งานส่วนหนึ่งเป็นต้นทุนคงที่ (poller ตัวจับเวลาทุก 0.5 วิ, heartbeat, Redis pub/sub ที่รวมข้อความหลายโต๊ะ) และผู้เล่นต่อคนเพิ่มงานน้อยลงเมื่อเครื่องมีงานต่อเนื่อง
- **t3.micro มี 2 vCPU แต่ Node.js ใช้ 1 core → ~50 % = core เต็ม** • ที่ 1,000 คนใช้ไปราวครึ่ง core
- ประมาณความจุต่อเครื่อง:
  - **แบบปลอดภัย:** ถ้าเกิน 1,000 คนแล้ว CPU กลับโตเร็วเท่าช่วงแรก (0.046 %/คน — ความชันแย่ที่สุดที่วัดได้) → ถึง 35 % (70 % ของ core) ที่ **~1,200 คน**
  - **ตามแนวโน้มจริง:** ความชันช่วงท้าย 0.013 %/คน → core เต็มราว **~2,900 คน** — เกินจากที่ทดสอบมาก จึงเขียนในรายงานว่า "**~2,000 คน**" (เผื่อไว้)
  - ตัวเลข CPU ทุกขั้นรวมงานของบัคตัวจับเวลาค้าง (ข้อ 7) ไว้ด้วย → ความจุจริงหลังแก้บัคน่าจะสูงกว่านี้เล็กน้อย
- **ทั้งระบบ:** Backend เพิ่มเครื่องได้ผ่าน ASG (Redis pub/sub ส่งสถานะโต๊ะข้ามเครื่องอยู่แล้ว) — ตัวถัดไปที่จะตันคือ Redis (ข้อ 5)

**1.2 RAM** — Node.js 130.0 → 132.6 → 135.9 MB (300 → 700 → 1,000 คน) ≈ **+8 KB ต่อผู้เล่น** • เครื่องใช้ ~290 MB จาก 913 MB → **RAM ไม่ใช่ข้อจำกัด**

**1.3 Latency**
- **p50 คงที่ 307 ms ทุกขั้น** = ผู้เล่นส่วนใหญ่ไม่รู้สึกต่างเลยตั้งแต่ 10 ถึง 1,000 คน
- p95 ขั้น 700 = 627 ms สูงกว่าขั้น 1,000 (417 ms) — `bots-timeline.csv` ของขั้น 700 แสดงว่า p95 **สูงตั้งแต่บรรทัดแรกที่นั่งครบ (643 ms) แล้วค่อยๆ ลดลงระหว่างเล่น (627 ms)** → ช่วงที่ช้าคือ **ระหว่างจัดโต๊ะ** (21:04–21:18) ที่บอทซึ่งนั่งก่อนเริ่มเล่นไปพร้อมกับที่บอทอื่นกำลังเข้าห้องจำนวนมาก (การเข้าห้องต้องเช็คกระเป๋าเงินใน DB + กระจายสถานะให้ทั้งโต๊ะ) — ตัวเลข latency ของบอทเป็นค่าสะสมตั้งแต่มือแรก จึงรวมช่วงนั้นด้วย
- ข้อสังเกตสำหรับรายงาน: **การเข้าห้องพร้อมกันจำนวนมาก (join storm) หนักกว่าการเล่นปกติ** — ช่วงเปิดเซิร์ฟเวอร์ใหม่ / หลัง deploy ควรระวัง

### 2. Load Balancer
- เวลาตอบ REST ใน AWS: p50 10–14 ms, **p95 20–22 ms ทุกขั้น** (ไม่ขึ้นตามผู้เล่นเลย), p99 63–115 ms
- เชื่อมต่อค้าง: 603 → 2,112 → **2,498** (~2.5 ต่อผู้เล่น — นับทั้ง WebSocket และ HTTP)
- 5xx: 1 ครั้งที่ 700 คน (จาก 295 คำขอ = 0.3 %) และ 1 ครั้งในหน้ารายชื่อห้องที่บอทเห็น (1 จาก 297) — นอกนั้น 0
- Frontend (nginx) CPU 1.5 → 3.3 % — ไม่ใช่คอขวด

### 3. RDS — writer
- CPU เฉลี่ย 4.5 % (ว่าง) → 5.6 → 7.2 → **8.0 %** ที่ 1,000 คน
- Write IOPS 100 → 125 → **153** (≈ 0.15 ต่อผู้เล่น) — gp3 ให้ 3,000 IOPS พื้นฐาน
- Write latency **0.77 → 0.69 → 0.68 ms** (ไม่ช้าลงเลย)
- Connections 15 คงที่ (connection pool) • Free memory ~110 MB คงที่
- Replica lag สูงสุด 1 s ทุกขั้น (ปกติ 0)

### 4. RDS — พิสูจน์ว่า read replica ถูกใช้จริง
กราฟ Read IOPS ของ replica แทบเป็น 0 (ข้อมูลอยู่ใน RAM ของ MySQL ไม่ต้องอ่านดิสก์) และ performance_schema ปิดอยู่ (ค่าเริ่มต้นของ RDS เครื่องเล็ก) จึง **นับจำนวน SELECT ที่แต่ละเครื่องตอบโดยตรง** (`SHOW GLOBAL STATUS` ผ่าน SSM — `tools/loadtest/db-counters.mjs`) แล้วเทียบ 2 ช่วง:

| เครื่อง | ช่วงว่าง (21:57–22:03, 6.3 นาที) | ช่วงบอทเปิดหน้ารายชื่อห้อง/ประวัติ (22:03–22:09, 5.4 นาที, 444 ครั้ง) | SELECT ที่เพิ่มจากแอป |
|---|---|---|---|
| writer | 191 /นาที | 223 /นาที | +170 (มาจากบอท 8 ตัวที่เล่นอยู่ — งานเกมอ่าน/เขียนที่ writer) |
| **read-1** | 89 /นาที | 122 /นาที | **+172** |
| **read-2** | 81 /นาที | 134 /นาที | **+283** |
| **read-3** | 89 /นาที | 122 /นาที | **+179** |

- SELECT ช่วงว่าง (~85/นาที/เครื่อง) คือ query ตรวจสุขภาพของ RDS เอง
- คาดว่าแอปจะส่ง: 444 ครั้ง × (รายชื่อห้อง 1 query, ประวัติมือ 2, ธุรกรรม 2 → เฉลี่ย 5/3) ≈ **740 SELECT** กระจายให้ replica 3 ตัว ≈ 247 ตัวละ
- วัดได้ **634 SELECT** (ตัวละ 172–283) — **ตรงกับที่คาด ~86 %** (ส่วนต่างอยู่ในช่วงความคลาดเคลื่อนของ query ตรวจสุขภาพ) และกระจายครบทั้ง 3 ตัว
- → **ระบบส่งงานอ่านหน้ารายชื่อห้อง/ประวัติไปที่ read replica แบบวนรอบ (round-robin) จริง** ส่วนงานเกมและยอดเงินอยู่ที่ writer ตามที่ออกแบบ

### 5. Redis
- CPU primary 6.2 → 10.6 → **12.5 %** • replica node ~5 % • memory 7.2 → 7.6 MB
- Network out ของ primary 134 → 277 → **363 MB ต่อ 5 นาที** — pub/sub กระจายสถานะโต๊ะ (ส่วนที่โตตามผู้เล่นมากที่สุดของ Redis)
- Redis ทำงาน thread เดียวเหมือน Node.js — ตามแนวโน้ม (~0.008 %/คน ช่วงท้าย) ยังรับได้หลายพันคนก่อนเป็นคอขวด

### 6. ขนาดข้อมูล (ตัวเลขที่ควรใช้ในรายงาน)
วัด `information_schema` ก่อนขั้น 1 และหลังขั้น 3:

| | ก่อน | หลัง | เพิ่ม |
|---|---|---|---|
| hand_results (แถว / data+index) | 6,461 / 2,408,448 B | 31,450 / 10,010,624 B | +24,989 แถว / +7,602,176 B |
| transactions (แถว / data+index) | 7,331 / 3,489,792 B | 31,358 / 11,059,200 B | +24,027 แถว / +7,569,408 B |

- **ผู้เล่น 1 คน 1 มือ ≈ (7,602,176 + 7,569,408) ÷ 24,989 ≈ 0.61 KB** • ค่าเฉลี่ยทั้งตาราง (318 B + 0.96 × 353 B) ≈ 0.65 KB — สองวิธีตรงกัน
- Test1 ได้ 1.14 KB เพราะข้อมูลน้อย (MySQL จองพื้นที่เป็นก้อนใหญ่ช่วงตารางเล็ก) — **ใช้ ~0.65 KB จาก Test2** (ข้อมูลมากกว่า 8 เท่า)
- ประมาณการ: 180 มือ/คน/วัน × 0.65 KB ≈ **117 KB/คน/วัน** → ผู้เล่น 1,000 คน/วัน ≈ 117 MB/วัน → **20 GB เต็มใน ~170 วัน, 50 GB ใน ~430 วัน**

### 7. บัคที่เจอจากการทดสอบ — ตัวจับเวลาหลุดการเชื่อมต่อค้าง
- **อาการ:** หลังทดสอบ (ไม่มีผู้เล่นเลย) Backend CPU 5.9 % และ Redis 3.9 % ค้างอยู่ (ปกติ 1.1 % / 0.3 %) • ตรวจ Redis พบ `poker:disconnect-timers` **ค้าง 95 รายการที่ครบเวลาแล้ว**
- **สาเหตุ:** ตอนผู้เล่นหลุด ระบบตั้งเวลารอ 30 วิ — ถ้าครบเวลาแล้ว **ห้องถูกลบไปแล้ว / ผู้เล่นออกไปแล้ว / ต่อกลับมาแล้ว** โค้ดจบโดยไม่ลบรายการนั้น → poller ทำซ้ำทุก 0.5 วิ ตลอดไป (เกิดกับผู้เล่นจริงได้ เช่น กด "ออก" แล้วปิดหน้าเว็บทันที)
- **แก้:** `backend/src/ws/ws-server.js` → `handleLeaveRoom` ลบรายการทันทีเมื่อไม่ต้องใช้แล้ว (`[แก้บัค]`)
- **ยังไม่ได้ทดสอบบนระบบจริง** — ต้อง push แล้วเปลี่ยนเครื่อง Backend (ASG instance refresh) แล้วดูว่า CPU ตอนว่างกลับเป็น ~1 % และรายการไม่ค้าง

## ข้อจำกัด
1. บอทยิงจากคอมเครื่องเดียว IP เดียวในไทย (ระยะทาง ~260 ms, ลิมิต 100 คำขอ/นาที/IP ทำให้จัดโต๊ะใช้ 6–19 นาที)
2. บอทเล่นเร็วกว่าคนจริง → โหลดต่อคนสูงกว่าจริง
3. Latency ของบอทเป็นค่าสะสมตั้งแต่มือแรก (รวมช่วงจัดโต๊ะ)
4. ยังไม่ถึงจุดที่ Backend ตัน (CPU สูงสุด 25 %) — ความจุสูงสุดเป็นการประมาณ
5. Backend 1 เครื่องตลอด, ยังไม่มีกฎ Auto Scaling (ดู Test3 ถ้าทำ)
