## ความจุ (ตัวเลขสำหรับรายงาน)

- **ต่อ Backend (t3.micro):** ~1,820 คน = CPU ~37 % (core เต็มที่ 50 %) → **~2,400 คนต่อเครื่องก่อน core เต็ม**, ใช้จริงควรไม่เกิน **~1,500 คน/เครื่อง** (≈ 30 %) — ตรงกับเป้า Auto Scaling 25–30 % ที่แนะนำ
- **ต่อ Frontend (t3.micro, หลังแก้ nginx):** ~2,500 คน = CPU 8 % → ไม่ใช่ข้อจำกัด
- **RDS writer (db.t4g.micro):** 23 % / 681 IOPS ที่ 5,000 คน → เหลือที่ว่างอีกหลายเท่า
- **Redis (cache.t3.micro, thread เดียว):** **45 %** ที่ 5,000 คน, network out ~7.6 MB/วินาที → **ตัวแรกที่จะตันถ้าไปถึง ~10,000 คน** (เพราะ pub/sub ส่งทุกเหตุการณ์ของทุกห้องให้ทุก Backend)
- ขนาดข้อมูล: hand_results +88,799 แถว (+25.2 MB), transactions +85,309 (+25.2 MB) → **0.57 KB / ผู้เล่น / มือ** (สอดคล้อง Test2–5)

## ข้อเสนอต่อจากผลนี้

1. **เป้า Auto Scaling 25–30 %** สำหรับระบบจริง (12 % ใช้เพื่อทดสอบ)
2. **Target group `least_outstanding_requests`** — ให้เครื่องใหม่รับคนใหม่ก่อน จะได้ไม่มีเครื่องที่ถือ 1,800 คนข้างเครื่องที่ถือ 680
3. **Redis:** เพิ่มขนาด node หรือเปลี่ยน pub/sub เป็นช่องต่อห้อง ให้แต่ละ Backend subscribe เฉพาะห้องที่มีผู้เล่นของตัวเอง
4. `GET /tables` แบ่งหน้า • RDS Proxy เมื่อเกิน ~6 Backend

## ข้อจำกัด
1. Latency เป็นค่าสะสมรวมช่วงจัดโต๊ะ (ตอนนั่งครบ p50 294 / p95 401 → ตอนจบ 296 / 410 = ช่วงเล่นนิ่ง)
2. บอทยิงจากคอมเครื่องเดียวในไทย (~260 ms) • บอทเล่นเร็วกว่าคน → โหลดต่อคนสูงกว่าจริง
3. Backend ใน Test6 เปิดใหม่ก่อนเริ่ม ~8 นาที → baseline 1.5 % (Test5 0.5 %)
